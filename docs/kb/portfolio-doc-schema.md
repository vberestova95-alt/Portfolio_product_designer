| Трекеры: логика и референсы | Модель · Каталог инструментов · Сценарии · Как задачи попадают в список · Практики формирования привычки · Референсы (карта рынка) · Открытые вопросы · Источники | предметная логика продукта + разбор рынка со ссылками |
| Ретроспектива процесса | Саммари дней (новые сверху; H3 на дату: «Что сделано по ролям» Роль / Что / Источник, «Решения пользователя» Решение / Почему / Источник, «Дальше») · Пайплайн, как он сложился (№ / этап / дата / вход / артефакт / что запустило следующий шаг) · Правки и их основания (Дата / Правка / Основание / Вывод) · Правила, которые выросли из правок · Коммуникация · Артефакты · Заготовка для скилла ведения проекта · Журнал ретро по сессиям (одна строка на сессию) · Выводы и предложения по процессу (новые сверху) | решения — всегда с «почему» и источником (коммит, R2·N, node-id); история — по датам, новые сверху; правило — только если подтвердилось дважды |

Названия разделов «Трекеров» после «Каталог инструментов» («Как задачи…», «Практики ф…», «Референсы…») сняты по сокращённому оглавлению — дописаны по смыслу.

Что берём: вкладки слева; продукт отдельно от процесса и от команды; «новые сверху»; решение → почему → источник;
сводка задач = зеркало `BACKLOG.md` / `FUTURE.md`, а не второй бэклог.

## 2. Предлагаемая схема — 4 вкладки (+ по вкладке на кейс)

### (а) «Портфолио как продукт»
| Подраздел | Что там | Откуда данные | Кто ведёт |
|---|---|---|---|
| Зачем делаем | цель сайта, что должно случиться после просмотра (контакт, интервью) | `docs/kb/context.md` «Что это и зачем» | docs-keeper, правит пользователь |
| Для кого | нанимающие менеджеры, дизайн-лиды: что ищут, сколько времени, с какого устройства | `docs/kb/context.md` «Для кого»; `research/` | researcher |
| На что опираемся | принципы сайта продуктового дизайнера: кейс как история решения, 3 главных кейса в хиро, EN + RU | `research/`, `docs/kb/decisions.md` | researcher → docs-keeper |
| Метрики | что собираем и где: визиты и переходы по кейсам (`api/collect.js`, дашборд `/stats`, Upstash Redis), Яндекс Метрика; срез по датам | `api/` + `/stats`, Метрика | docs-keeper (раз в неделю), цифры снимает пользователь или developer |
| Гипотезы | формат как у Fluffy Chumb: гипотеза / как проверяем / критерий / статус | решения пользователя, `docs/kb/decisions.md` | docs-keeper + researcher |
| Выводы | что подтвердилось по метрикам и отзывам | метрики, сообщения пользователя с датой | docs-keeper |
| Что меняем и почему | решения по сайту: решение → почему → источник | `docs/kb/decisions.md` | docs-keeper (через `/kb-session-summary`) |
| История по датам | новые сверху: деплои, крупные изменения | git log `Portfolio_product_designer` и `Portfolio_product_designer_site` (`deploy: publish …`) | docs-keeper |
| Статус кейсов + сводка задач | таблица кейсов; «В работе» ← `BACKLOG.md`, «Отложено» ← `FUTURE.md`, строка на пункт | `BACKLOG.md`, `FUTURE.md` | docs-keeper |

### (б) Кейс — вкладка на каждый кейс, подразделы одинаковые
Окончательный список подразделов — по шаблону п. 12 (editor). Предварительно:
| Подраздел | Откуда данные | Кто ведёт |
|---|---|---|
| Статус и задачи кейса | `BACKLOG.md`, `DESIGN-REVIEW.md` | docs-keeper |
| Источник: проект, ссылки, «Сверено» | `docs/kb/projects.md` | docs-keeper |
| Факты и история проекта (решение → почему → источник) | `docs/kb/projects/<проект>.md`, `research/` | docs-keeper, researcher |
| Черновик текста EN + RU по структуре кейса (проблема → контекст и роль → исследование → сценарии → решения → метрики → выводы) | факты выше | editor |
| Картинки: обложка, лента, кадры с node-id | Figma портфолио, `scripts/build-case-frames.mjs`, `DESIGN-REVIEW.md` | designer, design-sync |
| Открытые вопросы к пользователю | все выше | любая роль, сводит docs-keeper |
Первая вкладка — Fluffy Chumb (перенос нынешнего H1 «Fluffy Chumb»); остальные кейсы — по решению пользователя.

### (в) «Команда агентов и правила» — отдельно от кейсов
| Подраздел | Откуда данные | Кто ведёт |
|---|---|---|
| Роли, кто сейчас в какой роли | `TEAM.md` | docs-keeper (копия; правит TEAM.md оркестратор) |

| Где что лежит (реестр проектов) | `docs/kb/projects.md` | docs-keeper |

### (г) «Саммари дня и ретро»
| Подраздел | Откуда данные | Кто ведёт |
|---|---|---|
| Саммари дней (новые сверху; на дату: что сделано по ролям — Роль / Что / Источник; решения пользователя — Решение / Почему / Источник; дальше) | `ЗНАНИЯ` ролей, git log, `BACKLOG.md`, `docs/kb/sessions/` | docs-keeper |

| Скорость: от просьбы до деплоя, коммиты и деплои в день | git log обоих репозиториев | docs-keeper (данные для п. 13 — researcher) |

## 3. Перенос (после «да»)
- Нынешний H1 «Обзор портфолио» → вкладки (а) («Статус кейсов», «Задачи») и (в) («Команда агентов»); «Как пользоваться» — в начало (а).
- H1 «Fluffy Chumb» → вкладка кейса (б) целиком, без переписывания; статусы чек-листов сохраняем.
- Вкладка (г) — новая, пустая с первой датой.
- Риск из п. 6: при переносе блоков между вкладками могут потеряться статусы чек-листов, схема и ссылки — переносить блоками с проверкой после каждого, когда editor не работает в документе.
